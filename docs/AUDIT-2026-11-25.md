# Infrared security and maintenance audit - 25 November 2026

This audit covers the current website-project changes and their interaction with authentication, authorization, browser telemetry, input validation, installation checks, storage, and backup recovery. It is a source review with local automated verification, not a certification of a deployed service.

## Confirmed findings and fixes

| Finding | Result |
| --- | --- |
| Archived sites were hidden from bootstrap but could still be accessed through direct management routes and membership lists. | Shared authorization now excludes archived sites for owners and members. Browser ingestion and backend acquisition also reject archived projects. |
| An administrator could switch an owner-approved real website from selected pages to whole-site collection. | Changing collection settings on an enabled, approved real site requires the owner. Running or paused experiments also lock these settings. |
| Production restrictions on synthetic browser traffic were missing from backend acquisition eligibility. | Both collection paths now reject synthetic projects in production. |
| Approved real websites were always labeled as disabled by installation status. | Status now follows archive state, enablement, approval, and the global collection stop. |
| Structural discovery could reuse a website-owned identifier or remove/overwrite host attributes during cleanup. | Discovery avoids reserved identifiers, restores previous exposure attributes, and preserves subsequent website changes. Private regions remain excluded. |
| Exposure qualification checked vertical visibility only. | Qualification now measures visible area in both axes. Elements outside the viewport cannot qualify. |
| Distinct paths could share automatic keys: `/` and `/home`, `/a/b` and `/a.b`, different case, and literal reserved slugs. | Ambiguous paths receive a deterministic suffix. Existing ordinary path keys remain stable. |
| Sensitive root exclusions such as `/login` and `/cart` did not cover child paths. | Those exclusions now protect their descendants too. Explicit site rules still control collection. |
| Saving site collection settings erased discovered page element/action registries. | Updates preserve discovered entries and enforce combined size limits. Discovery ingestion also avoids repeated writes when the registry has not changed. |
| New sites had no primary conversion goal, but policy validation required a nonempty registered CTA/action. | Unconfigured primary goals are now valid and visible in the selector, while unknown nonempty identifiers remain rejected. |
| Concurrent project creation could surface a database uniqueness error as an internal error. | Origin conflicts are handled as a controlled conflict response; brand labels also reject control characters. |
| Restore checked only whether sites existed, so an account-only destination was incorrectly considered empty. | Restore checks all application tables plus sessions, retains checksum validation, cleans up newly written reference files on transaction failure, and keeps historical example projects disabled. The CLI and tests use the same recovery implementation. |
| Private reference writes inherited permissive file creation defaults on POSIX systems. | New reference directories request mode `0700` and files request `0600`, retaining exclusive creation. Windows access continues to depend on inherited ACLs. |

## Practical limits and follow-up validation

- Browser E2E scenarios were not executed during this audit. Several existing scenarios still describe the former demo-led interface and need adaptation before they can validate the Projects workflow. Unit/integration tests do not replace browser validation.
- The database tests use PGlite. PostgreSQL deployment behavior, proxy/TLS configuration, simultaneous client transactions under load, and production operation were not exercised.
- Automatic element names are structural. Layout changes can change their numbering; business categories and completed conversions are not inferred.
- Ambiguous paths fixed by this audit can begin a new automatic page cohort. Existing historical records are preserved.
- This audit does not deploy changes, restart an existing service, rotate credentials, or modify the user's live database.

## XSS and server follow-up

Reviewed the dashboard's HTML/script/URL rendering paths, generated installation snippets, management response types and security headers, session/CSRF boundaries, SQL identifier allowlists, upload/storage boundaries, request-body limits, installation probes, and trusted-edge address parsing.

No direct XSS exploit was identified in the inspected rendering paths. Added regression checks for stored hostile project names/brands rendered through React, reflected query payloads, JavaScript literal escaping, and early script termination in the generated installation endpoint. These checks cover server-rendered markup and generated code; they are not a substitute for executing the dashboard in a browser.

A confirmed configuration vulnerability was fixed: an empty CIDR suffix such as `TRUSTED_PROXIES=10.0.0.0/` previously converted to prefix zero and trusted all IPv4 addresses. Empty, noncanonical and extra CIDR components are now rejected rather than silently broadening proxy trust.

Management responses now explicitly disable embedded objects through CSP and set same-origin opener and resource policies. The collector's public SDK/CORS behavior remains separate.

Additional checks verify SQL-shaped sort rejection, private-file traversal rejection, oversized-body rejection before persistence, secure HttpOnly/SameSite cookies and HSTS under HTTPS configuration, and refusal to follow a registered website's redirect to the cloud metadata address. The focused security command now includes the new regression suites.

Follow-up verification: strict type checking passed; all 35 Vitest files passed with 215 passed tests and the same 2 optional Python tests skipped. Browser E2E and a deployed server were not verified.

## Current local runtime

Optional hosted PostgreSQL/Supabase connection configuration is prepared with private-schema isolation and verified TLS, but no hosted account or database has been connected.

Final native verification after these changes: 36 Vitest files passed, 220 tests passed, 2 optional Python tests skipped; strict type checking and diff checks passed. The read-only connection checker confirms local PGlite mode with DATABASE_URL unset. Existing local database files were not migrated or deleted by this setup removal.

## Project setup and dashboard follow-up

The selected website now scopes dashboard landing pages, campaign analytics, acquisition, experiments, registry imports/exports, installation status, data-quality totals, and the paginated audit trail. Switching projects resets page-specific screens and filters; the selected project persists across browser reloads. Slow responses are associated with their original report query so they cannot display another project's report.

Creating a project transactionally prepares its Home page, whole-site rules, site key and tracking configuration. The installation screen loads its script automatically and refreshes activity status every 15 seconds. Owner approval enables pending automatic pages while preserving explicitly paused pages. Static pixel inspection and received activity remain distinct signals. Installing a script on an external website, granting visitor consent, connecting marketing accounts, and defining business conversion goals still require the corresponding integration or decision; project creation does not fabricate traffic or integrations.

Manual page preparation and registry imports in whole-site mode now use the same canonical paths, generated page keys and automatic context as browser discovery. Unsupported query-specific identities and manual automatic-context changes are rejected. Custom product labels such as clothing and services are accepted. Page creation and imports with an explicit project reject other website origins.

The project form uses stacked labels, consistent 46px inputs, 24px field gaps, 28px card padding and responsive single-column fields. Installation setup, script controls and status sections have explicit spacing.

Browser validation used a disposable in-memory PGlite server on port 3035, separate from the user's existing database. Confirmed creation of two projects, automatic Home-page preparation, automatic script loading, manual page preparation, isolation after switching websites, selected-project persistence after reload, and form layout at desktop and 390px widths. No browser console errors were observed in that workflow. This supplements the local automated checks; it does not verify installation on an external website or deployed PostgreSQL operation.

Workspace operations, privacy/retention settings and transient rejected-request counters remain explicitly workspace-wide.

## Asset rebuild repair

The running server's `wildcard:false` static registration enumerated build filenames only at startup. Rebuilding changed hashed CSS/JavaScript filenames, so the existing process returned JSON 404 responses for assets referenced by the new HTML. Replaced that obsolete registration with request-time static resolution, explicitly excluded hidden paths, and disabled caching of the HTML entry point and theme initialization. Builds preserve previous chunks needed by already-open browser tabs. Removed the unused font preload that generated the separate browser warning.

Added a regression test that creates a CSS asset after the management server is ready and verifies HTTP 200, `text/css`, the file contents, a real 404 for a nonexistent asset, and `no-store` for the HTML entry point. The full suite passed with 227 tests and 2 optional Python tests skipped before this final asset regression; the subsequent affected security, project, management and table suites passed all 35 tests. Strict type checking, dashboard production build, release artifact checks and diff checks passed.

Applying the server change requires restarting the existing local process. The attempted stop of PID 9204 was denied by Windows; that process was left running and its database was not copied, deleted or opened by another process. The user was asked to restart Infrared from their terminal. The rebuilt dashboard is ready on disk.

The user subsequently restarted Infrared. Live checks against port 3000 confirmed HTTP 200 for the dashboard, theme initialization, generated JavaScript and stylesheet, with correct JavaScript/CSS MIME types. A subsequent rebuild was served successfully by the same restarted service.

Publisher attribution, obsolete logo/icon files, unused branding selectors and the old stylesheet filename were removed at the user's request. The app title and shared login/sidebar/footer identity now contain only Infrared. Superseded generated bundles were removed after checking the current entry point's asset dependency graph. Current entry, stylesheet, main JavaScript and chart JavaScript all return HTTP 200. Type checking and the production build passed after the cleanup.
